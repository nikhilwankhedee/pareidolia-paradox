H. AUDIT CONCLUSION
==========================================================================================

1. IS THE DATASET EFFECTIVELY GRAYSCALE?

   YES. All sampled images have R == G == B exactly.
   The dataset is effectively single-channel, stored as RGB.
   Models can conceptually treat input as 1-channel, but should
   retain 3-channel input for pretrained CNN compatibility.

2. IS TRAIN/TEST EXACT IMAGE OVERLAP REAL?

   YES. 829 unique image hashes appear in both train and test.
   This covers 829 unique test images (41.4% of test set).
   These are byte-identical images, not similar or near-duplicates.

3. ARE OVERLAPPING IMAGES USUALLY ASSOCIATED WITH THE SAME OR DIFFERENT AZIMUTH?

   0 row-pairs (0.0%) have SAME azimuth.
   829 row-pairs (100.0%) have DIFFERENT azimuth.
   Median circular azimuth difference: 88.18
   Max circular azimuth difference: 179.81

4. ARE TRAIN DUPLICATE LABELS CONSISTENT?

   NO. All 1458 train duplicate groups are label-CONFLICTING.
   Identical pixel content is labeled BOTH class 0 and class 1
   (2916 images / 1458 groups).
   CRITICAL: The label is NOT a function of pixel content alone.
   The same exact image is labeled Depth in one row and Rise in another.
   Therefore the class must be (at least partly) determined by the
   azimuth/lighting metadata + geometry, not the static 2D pixels.

5. WHAT DOES THE OVERLAP LOOK LIKE?

   The 829 shared hashes are exact pixel copies.
   Every cross-split pair (829/829) has a DIFFERENT azimuth
   (median circular diff ~88 deg). The same physical surface patch
   appears in both splits with different sun illumination angles -
   consistent with repeated orbital pass imagery of the same crater/mound.
   Within train, identical pixels recur 1458 times with
   DIFFERENT labels AND different azimuths - i.e. the same patch was
   imaged under two lighting conditions and given opposite labels,
   because the lighting determines which shadow-based cue (depth vs rise)
   is visible. This is a construction artifact tied to the lighting geometry,
   not a random labeling error.

6. IMPLICATIONS FOR:

   - VALIDATION DESIGN:
     829 shared hashes leak train/test. Random CV overstates
     performance. Use hash-grouped CV (never split identical pixels across
     folds) to measure generalization honestly.

   - IMAGE MEMORIZATION:
     829/2000 (41.4%) of test images
     exist byte-identical in train - a memorization shortcut exists. BUT
     because labels are azimuth-dependent and the shared images have DIFFERENT
     azimuths in train vs test, memorizing the train label is NOT sufficient.
     The azimuth (lighting) must be incorporated to label a shared image correctly.

   - AZIMUTH HANDLING:
     Azimuth is NOT a confound to be purged - it is LIKELY RELEVANT TO THE LABEL.
     Identical pixels get opposite labels based on lighting direction. The
     77.6% azimuth-only balanced accuracy reflects real label-azimuth coupling,
     not just an artifact. The model MUST use azimuth together with pixels.

   - ORGANIZER-PRESCRIBED -sun_azimuth ROTATION:
     Rotating by -sun_azimuth_angle normalizes illumination so that the sun
     direction becomes consistent across images. This is likely the intended
     way to make lighting-independent geometry (crater vs mound) comparable.
     Under rotation, identical patches imaged at different azimuths should
     ALIGN, so the same surface should produce the SAME class after rotation.
     This rotation is probably ESSENTIAL for correct classification.

7. RECOMMENDED NEXT EXPERIMENT:

   Test the organizer-prescribed -sun_azimuth rotation hypothesis directly:
   take the train duplicate groups (identical pixels, opposite labels, different
   azimuth) and rotate each image by its -sun_azimuth_angle. If the rotation is
   correct, the aligned (rotated) duplicate pairs should produce images that the
   model can classify consistently. Concretely: rotate all train images by
   -sun_azimuth_angle, then train a small model on the rotated pixels and measure
   whether duplicate pairs become label-consistent (should approach 100% if the
   rotation reveals the true geometry). This tests whether rotation resolves
   the labeling ambiguity before committing to any architecture.
